Abstract

MusicChain is a three-tier decentralized protocol for music distribution, royalty settlement, and audio-anchored blockchain consensus. Blocks are cryptographically anchored to unique audio fingerprint constellations generated by a C++ port of the Dejavu algorithm (Wang, 2003), compiled to WebAssembly for browser-based storage nodes. A self-regulating token economy oscillates between 1B–2B tokens on a 2-year sine wave cycle, governed by dynamic mint/burn rates responsive to supply ratio. Artist royalties settle automatically into dual escrow wallets (master + publishing). Storage nodes earn passively by serving audio files. Downloaders earn tokens by discovering songs under 10,000 downloads and spend tokens to access popular content above the threshold, burning tokens from their wallet per download.

Full song metadata is stored on-chain at registration time as a complete ID3v2.4 tag record including title, artist, album, composer, genre, BPM, musical key, ISRC, publisher, copyright, language, cover art hash, and lyrics hash — making every song registration a permanent, immutable, cryptographically attributed metadata record tied to its audio fingerprint.

Full nodes are C++ console applications built from open source Bitcoin Core primitives and libbtc. MusicChain is released under the GNU General Public License v3.0 (GPL-3.0). They host the blockchain, fingerprint registry, dual escrow system, and a Gitea Git server whose commits are watched by a C++ commit watcher process. Approved commits earn token rewards to developer wallets — creating a self-funded, decentralized open source development model built into the protocol itself.

The storage node application is a single HTML/JavaScript/WebAssembly page, served uniformly across desktop browsers and Flutter mobile shells. C libraries (Dejavu, KissFFT, libsecp256k1) are compiled to WebAssembly via Emscripten and called directly from JavaScript with near-native performance. Audio files are persisted to the device hard drive via the Origin Private File System (OPFS) API. The Flutter mobile app is a thin WebView shell exposing native capabilities (background service, biometric auth, push notifications) via a JavaScript bridge.

2. Proof of Creativity: Audio-Anchored Consensus

2.1 The Consensus Model

MusicChain's consensus mechanism is fundamentally unlike any existing blockchain. There are no fixed block intervals, no proof-of-work hash targets, no validator schedules, and no staking requirements. Instead, the chain advances one block at a time, and each block is produced by exactly one event: the network reaching consensus that a newly submitted audio fingerprint constellation is genuinely unique — that no song with this acoustic signature has ever been registered before.

Block production trigger:

  1. Artist uploads audio file to full node

  2. Full node generates Dejavu fingerprint constellation

  3. Full node checks constellation against fingerprint registry

  4. If no match found: novel fingerprint confirmed

  5. Nodes reach consensus: this fingerprint is unique

  6. Fingerprint constellation becomes the next block

  7. All accumulated transactions since the last block

     are swept into this block's transaction set

  8. Block is added to the chain

  9. Chain height advances by 1

The block rate is therefore entirely variable — determined by how many genuinely unique songs are being registered. The chain cannot be artificially accelerated. There is no computational shortcut to producing a block. A block requires a real song that no one has ever registered before.

2.2 Proof of Creativity

This consensus model constitutes a new class of blockchain consensus: Proof of Creativity.

Proof of Work:    advance the chain by expending compute

Proof of Stake:   advance the chain by locking capital

Proof of Creativity: advance the chain by contributing

                  something genuinely new to human culture

The implications are significant:

Spam resistance by design. You cannot flood the chain with fake blocks because each block requires a genuinely unique audio file. Submitting a previously registered song produces no block — the fingerprint registry rejects it immediately. Submitting noise or silence produces a fingerprint that matches no song but also earns no economic reward, making it irrational.

No mining arms race. Block production cannot be accelerated by purchasing more hardware. A recording studio with 1,000 servers produces blocks at exactly the same rate as an independent artist with a laptop — one block per unique song registered.

The chain is the catalog. Every block is a song. The blockchain does not merely reference music — it is the music catalog. Chain height equals the number of unique songs ever registered on the network. This is a fundamentally different relationship between a blockchain and its content than any prior design.

Cultural output is the ledger. The chain's block history is a permanent, immutable, cryptographically ordered record of human musical creativity. A slow chain means a creatively quiet period. A fast chain means a creative explosion. Block timestamps are not clock-driven — they are creativity-driven.

2.3 Variable Block Rate and Network Throughput

Because block rate is driven by upload volume, network throughput scales automatically with creative adoption. Play and download events accumulate between blocks in the mempool and are swept into the transaction set of the next block when a new song is registered.

Block interval = time between unique song registrations

Transaction throughput = accumulated events ÷ block interval



At low upload volume:

  Few blocks per day → longer intervals → more events per block

  Chain is lean, event backlog clears on each new song



At high upload volume:

  Many blocks per day → shorter intervals → fewer events per block

  Chain advances rapidly, event confirmation is near-instant

This self-regulating property means the network never becomes congested by listener activity alone. Listener-generated events (plays and downloads) are always bounded by the upload rate, which determines how frequently the mempool is flushed.

2.5 Fingerprint Uniqueness Consensus

Node consensus on fingerprint uniqueness uses the existing librats GossipSub layer. When a full node receives a new song upload, it generates a Dejavu fingerprint constellation and broadcasts the hash to all peer full nodes. Each peer independently queries its local fingerprint registry (SQLite) for a match. The outcome branches on whether the song is genuinely new or a known song in a different format or bitrate.

Path A — Novel song (no match found):

  1. Full node A receives upload → generates constellation C

  2. A computes H = SHA256(C)

  3. A broadcasts FINGERPRINT_PROPOSE{H, C} to all full node peers

  4. Each peer: query local SQLite for H → no match → reply UNIQUE_CONFIRM{H}

  5. A collects UNIQUE_CONFIRM from ≥51% of full nodes

  6. A broadcasts BLOCK_PROPOSE{prev_hash, H, C, transactions[]}

  7. Peers validate block → add to chain → broadcast confirmation

  8. Block is final — song registered, new source entry created

Path B — Known song (match found — duplicate fingerprint):

  1. Full node A receives upload → generates constellation C

  2. A computes H = SHA256(C)

  3. A broadcasts FINGERPRINT_PROPOSE{H, C} to all full node peers

  4. Each peer: query local SQLite → MATCH FOUND for existing song_id S

     → reply DUPLICATE_FOUND{H, song_id: S}

  5. A receives DUPLICATE_FOUND from ≥51% of full nodes

  6. No block produced — this is not a new song

  7. A instead broadcasts SOURCE_REGISTER tx (Type 0x0F):

       song_id:    S  (the existing registered song)

       node:       uploader's storage node wallet

       format:     container format (FLAC, MP3, OGG, AAC, OPUS...)

       bitrate:    kbps (uint16)

       file_hash:  SHA256 of this specific audio file

       file_size:  bytes (uint64)

  8. Full nodes add this source to S's availability map

  9. Uploader's storage node is now listed as a source for song S

     with its specific format and bitrate

  10. Uploader earns storage node rewards when their copy is downloaded

What this means in practice:

A song registered once as a 128kbps MP3 does not block others from contributing a 320kbps MP3, a lossless FLAC, or an Opus encode of the same recording. Each variant is a separate source entry in the song's availability map. The song has one canonical identity (one fingerprint, one block, one escrow) but many available sources differing in format and quality. Downloaders choose which source to fetch.

Conflict resolution (two novel songs submitted simultaneously):

  Both fingerprints are genuinely unique — both will eventually be blocks

  The one with more UNIQUE_CONFIRM votes at time of proposal wins round N

  The other becomes the first candidate for block N+1

  No song is lost — both get registered, just in sequential blocks

    final data = jsonDecode(msg.message);

    switch (data['cmd']) {



      // Wallet key storage — hardware-backed on both platforms

      case 'SECURE_WRITE':

        await _storage.write(key: data['key'], value: data['value']);

        _reply('SECURE_WRITE_OK', {'key': data['key']});



      case 'SECURE_READ':

        final val = await _storage.read(key: data['key']);

        _reply('SECURE_READ_OK', {'key': data['key'], 'value': val});



      // Biometric unlock for wallet

      case 'BIOMETRIC_AUTH':

        final ok = await _auth.authenticate(

          localizedReason: 'Unlock MusicChain wallet',

          options: const AuthenticationOptions(biometricOnly: true),

        );

        _reply('BIOMETRIC_RESULT', {'ok': ok});



      // Background keep-alive — critical for iOS where Service Workers are limited

      case 'BACKGROUND_PING':

        // Flutter background_service already running

        // Just acknowledge to JS

        _reply('BACKGROUND_PONG', {});



      // Native push notifications

      case 'NOTIFY':

        await showNativeNotification(data['title'], data['body']);



      // iOS audio session management

      case 'AUDIO_SESSION':

        await configureAudioSession(data['mode']);

    }

  }



  void _reply(String cmd, Map<String, dynamic> payload) {

    final json = jsonEncode({...payload, 'cmd': cmd});

    _controller.runJavaScript('mcFlutterReply($json)');

  }



  @override

  Widget build(BuildContext context) {

    return Scaffold(

      // Zero native chrome — HTML handles all UI

      body: SafeArea(child: WebViewWidget(controller: _controller)),

    );

4. WebAssembly (C Bindings in JavaScript)

4.1 WASM Overview

WebAssembly is the mechanism by which C/C++ libraries run in JavaScript environments at near-native speed. Emscripten compiles C/C++ to a .wasm binary plus a JavaScript glue file. JavaScript calls C functions directly via the WASM module's exported API. Memory is shared via a flat ArrayBuffer — C pointers become integer offsets into this buffer from JavaScript's perspective.

C/C++ source → Emscripten (clang + LLVM) → .wasm binary + .js glue

JavaScript: WebAssembly.instantiate(.wasm) → module

JavaScript calls: module.exports.my_c_function(arg1, arg2)

Performance: ~80-90% of native C speed in Chrome/Firefox

4.2 Dejavu C++ → WebAssembly Compilation

The Dejavu C++ port is compiled to WASM using Emscripten. The same C++ source used by full nodes and mini nodes compiles to WASM for the browser storage node — one codebase, three deployment targets.

Emscripten build command:

emcc \

  dejavu.cpp kissfft/kiss_fftr.c \

  -o dejavu.js \

  -s WASM=1 \

  -s EXPORTED_FUNCTIONS='["_mc_fingerprint_buffer","_mc_store_fingerprint","_mc_match_fingerprint","_mc_free_result","_malloc","_free"]' \

  -s EXPORTED_RUNTIME_METHODS='["ccall","cwrap","getValue","setValue"]' \

  -s ALLOW_MEMORY_GROWTH=1 \

  -s MODULARIZE=1 \

  -s EXPORT_NAME='DejavuModule' \

  -O3

JavaScript WASM API:

// fingerprint.js — Dejavu WASM orchestration

let dejavu = null



async function initFingerprint() {

  dejavu = await DejavuModule()

  

  // Wrap C functions for ergonomic JS calling

  _fingerprint = dejavu.cwrap('mc_fingerprint_buffer', 'number',

    ['number', 'number', 'number'])  // ptr, length, result_ptr

  _store = dejavu.cwrap('mc_store_fingerprint', 'number',

    ['string', 'number'])            // song_id, result_ptr

  _match = dejavu.cwrap('mc_match_fingerprint', 'number',

    ['number', 'number'])            // query_ptr, out_ptr

  _free = dejavu.cwrap('mc_free_result', null,

    ['number'])                      // result_ptr

}



async function fingerprintAudioBuffer(audioBuffer, songId) {

  // Convert AudioBuffer float samples to C-accessible memory

  const samples = audioBuffer.getChannelData(0)

  const byteLen = samples.length * 4

  const ptr = dejavu._malloc(byteLen)

  dejavu.HEAPF32.set(samples, ptr >> 2)



  // Call C fingerprint function

  const resultPtr = dejavu._malloc(64)  // FingerprintResult struct

  const status = _fingerprint(ptr, samples.length, resultPtr)



  if (status === 0) {

    // Extract constellation from result

    const hashCount  = dejavu.getValue(resultPtr + 8, 'i32')

    const constPtr   = dejavu.getValue(resultPtr + 4, 'i32')

    const constellation = new Float32Array(

      dejavu.HEAPF32.buffer, constPtr, hashCount * 3

    )



    // Store in local IndexedDB

    await storeFingerprint(songId, constellation)



    // Submit to full node via mini node

    await submitFingerprint(songId, constellation)

  }



  dejavu._free(ptr)

  _free(resultPtr)

}

4.3 PulseFFT — KissFFT as WebAssembly

PulseFFT (github.com/AWSM-WASM/PulseFFT) is KissFFT pre-compiled to WebAssembly. It is used inside the Dejavu WASM module but can also be called directly from JavaScript for real-time audio analysis in the player's waveform visualizer.

// Direct PulseFFT usage for waveform display

let pulse = {}

loadPulse().then(module => { pulse = module })



function computeWaveform(audioBuffer) {

  const fft = new pulse.fftReal(4096)

  const input = audioBuffer.getChannelData(0).slice(0, 4096)

  const spectrum = fft.forward(input)

  return spectrum  // frequency magnitude array for UI rendering

}

5. Fingerprint System

5.1 Library: C++ Port of Dejavu (Wang Algorithm)

Source: Dejavu Python (github.com/worldveil/dejavu) Algorithm: Wang, A. (2003). An Industrial Strength Audio Search Algorithm. ISMIR. Deployment targets:

  • Full nodes: native C++ binary, linked against KissFFT + SQLite3

  • Mini nodes: native C++ binary

  • Storage nodes: same C++ source compiled to WASM via Emscripten

C++ dependencies (native):

WASM dependencies (browser):

PulseFFT    AWSM-WASM/PulseFFT  KissFFT pre-compiled to WASM   MIT

Emscripten  emscripten.org      C++ → WASM compiler toolchain   MIT

Port procedure using Claude Code:

1. Feed Claude Code dejavu/fingerprint.py alongside KissFFT docs

2. Port module by module:

   a. audio_decode()      → libsndfile reader (native) / Web Audio API (WASM)

   b. fingerprint()       → KissFFT spectrogram + peak picker

   c. generate_hashes()   → constellation hash pairs

   d. store_fingerprint() → SQLite writer (native) / IndexedDB (WASM)

   e. find_matches()      → lookup + confidence scorer

3. Validate: compare Python vs C++ output hash sets on same audio file

4. Tune: adjust peak density until match accuracy equals Python Dejavu

5. Compile to WASM: emcc with exported function list above

6. Validate WASM: compare C++ vs WASM output on same audio buffer

Algorithm steps:

Step 1 — Spectrogram:

  FFT window:     4096 samples

  Hop size:       2048 samples (50% overlap)

  Window:         Hann

  Output:         time × frequency magnitude matrix

  Implementation: KissFFT kiss_fftr() / PulseFFT fftReal



Step 2 — Peak picking:

  Find local maxima in spectrogram

  Neighborhood:   ±10 Hz, ±100ms

  Amplitude threshold: configurable (default -20dB)

  Output:         constellation points {time, frequency, amplitude}



Step 3 — Hash pair generation:

  For each peak p1:

    For each peak p2 in fan_value=15 nearest neighbors:

      hash = SHA1(p1.freq | p2.freq | Δtime)[0:20]

      offset = p1.time

      store: (hash, offset, song_id)



Step 4 — Database storage:

  Native:  SQLite3 table fingerprints(hash TEXT, offset INT, song_id TEXT)

  Browser: IndexedDB store 'fingerprints' {hash, offset, songId}

  Index:   hash field for O(log n) lookup

  Size:    ~50-100KB per song at 25% density (reliable, storage-efficient)

5.2 Fingerprint Size Budget

Default density:  50,000-100,000 hashes per 3.5min song × 25 bytes = 1.25-2.5MB

25% density:      12,500-25,000 hashes × 25 bytes = ~300-600KB

On-chain:         SHA256(constellation) = 32 bytes canonical identifier

In block body:    full constellation at 25% density = ~400KB per block

IndexedDB:        25% density = ~100KB per song stored locally

5.3 Storage Node Processing Flow

Native (full nodes):

  1. Audio file F on disk

  2. mc_fingerprint_file(F) → constellation C

  3. SHA256(C) → fingerprint_hash H

  4. mc_store_fingerprint(song_id, C) → SQLite



Browser (storage nodes):

  1. Audio file F in OPFS

  2. Read F → ArrayBuffer → Web Audio API decode → AudioBuffer

  3. AudioBuffer → Float32Array PCM samples

  4. Pass to Dejavu WASM: mc_fingerprint_buffer(ptr, length, result)

  5. Extract constellation C from result struct

  6. SHA256(C) → fingerprint_hash H

  7. Store C in IndexedDB

  8. Submit {song_id, H, C} to full node via WebSocket → mini node relay

  9. Full node checks H against fingerprint registry

  10. Novel H → write into next block

  11. Storage node earns submission reward

6.1 Origin Private File System (OPFS) — Audio Files

OPFS provides near-native file I/O access to a private directory on the device's hard drive, invisible to the user's file manager but permanent across sessions. It is the primary store for audio files on storage nodes.

class AudioFileStore {

    const dir = await this._getSongsDir()

class MusicChainPlayer {

  constructor() {

    this.ctx       = new AudioContext()

    this.gainNode  = this.ctx.createGain()

    this.gainNode.connect(this.ctx.destination)

    this.source    = null

    this.queue     = []

    this.current   = null

    this.position  = 0

  }



  // Load and play from OPFS with 512KB initial buffer

  async play(songId) {

    const file = await store.retrieve(songId)



    // Stream first 512KB immediately for fast start

    const initialChunk = file.slice(0, 524288)  // 512KB

    const initialBuffer = await initialChunk.arrayBuffer()

    const audioBuffer = await this.ctx.decodeAudioData(initialBuffer)



    this.source = this.ctx.createBufferSource()

    this.source.buffer = audioBuffer

    this.source.connect(this.gainNode)

    this.source.start(0)



    // Load remainder in background

    this._loadRemainder(songId, file, 524288)



    this.current = songId

    this._trackPlay(songId)

  }



  async _loadRemainder(songId, file, offset) {

    // Load in 256KB chunks

    const CHUNK = 262144

    let pos = offset

    while (pos < file.size) {

      const chunk = file.slice(pos, pos + CHUNK)

      const buffer = await chunk.arrayBuffer()

      // Queue decoded chunk for seamless playback

      await this._queueChunk(buffer)

      pos += CHUNK

    }

  }



  // Track play events — 30 seconds = registered play

  _trackPlay(songId) {

    let elapsed = 0

    const timer = setInterval(() => {

      elapsed += 1

      if (elapsed >= 30) {

        clearInterval(timer)

        logPlayEvent(songId)  // analytics only, no token event

      }

    }, 1000)

  }



  setVolume(v) { this.gainNode.gain.value = Math.max(0, Math.min(1, v)) }

  pause()      { this.ctx.suspend() }

  resume()     { this.ctx.resume() }

}

7.2 Multi-node Chunk Selection

When fetching audio chunks from peer storage nodes, the best node is selected by a scoring algorithm weighted toward bitrate, then latency, then uptime.

// network.js — multi-node audio chunk delivery



async function fetchAudioChunks(songId, nodes) {

  // Score each node

  const scored = nodes.map(n => ({

    node: n,

    score: 0.5 * n.bitrate

          + 0.3 * (1 / Math.max(n.latencyMs, 1))

          + 0.2 * n.uptimePct

  })).sort((a, b) => b.score - a.score)



  const winner = scored[0].node



  // If multiple nodes have equal bitrate — split reward equally

  const topBitrate = scored[0].node.bitrate

  const tied = scored.filter(s => s.node.bitrate === topBitrate)

  if (tied.length > 1) {

    // Fetch chunks from all tied nodes in parallel

    return await fetchParallel(songId, tied.map(t => t.node))

  }



  return await fetchFromNode(songId, winner)

}

void processDownloadEvent(const Transaction& tx) {

  const auto songId = tx.song_id



  // Count confirmed download events for this song from chain

  uint64_t downloadCount = chainIndex.countTxType(

    TxType::DOWNLOAD_EVENT, songId

  )



  if (downloadCount <= 10000) {

    // Discovery phase — mint tokens

    float M = getCurrentMintRate()

    mintToWallet(tx.downloader,    M)         // downloader earns

    mintToWallet(tx.node_served,   1.0f)      // storage node earns

    mintToEscrow(songId, MASTER,   0.5f * M)  // master escrow

    mintToEscrow(songId, PUBLISH,  0.5f * M)  // publishing escrow



  } else {

    // Popular phase — burn from downloader, mint to others

    float B = getCurrentBurnRate()



    if (getBalance(tx.downloader) < B) {

      rejectTx("Insufficient balance for popular download")

      return

    }



    burnFromWallet(tx.downloader,   B)        // downloader burns B

    mintToWallet(tx.node_served,    1.0f)     // storage node always earns

    mintToEscrow(songId, MASTER,    0.5f)     // master escrow always earns

    mintToEscrow(songId, PUBLISH,   0.5f)     // publishing escrow always earns

// l2channel.js — state channel implementation



class StateChannel {

  constructor(myKeyPair, peerPublicKey, initialBalance) {

    this.myKeyPair      = myKeyPair

    this.peerPublicKey  = peerPublicKey

    this.state = {

      nonce:    0,

      balances: {

        mine: initialBalance,

        peer: 0

      },

      pendingBurns: 0

    }

    this.signatures = {}

  }



  // Update state for a download payment

  async recordDownload(songId, type, rate) {

    const newState = { ...this.state, nonce: this.state.nonce + 1 }



    if (type === 'earn') {

      // Discovery phase: mint M tokens to my wallet

      newState.balances.mine += rate



    } else if (type === 'burn') {

      // Popular phase: burn B tokens from my wallet

      if (newState.balances.mine < rate) {

        throw new Error('Insufficient balance for download')

      }

      newState.balances.mine     -= rate   // downloader pays

      newState.balances.peer     += 1      // storage node earns 1

      newState.pendingBurns      += (rate - 2)  // net burn

      // +0.5 master escrow and +0.5 publishing escrow

      // handled on L1 settlement separately

    }



    // Sign new state

    const stateHash = this._hashState(newState)

    const sig = this.myKeyPair.sign(stateHash)

    newState.mySignature = sig.toString('hex')



    this.state = newState

    return newState

  }



  // Hash state deterministically for signing

  _hashState(state) {

    return bitcoin.crypto.sha256(

      Buffer.from(JSON.stringify({

        nonce:        state.nonce,

        mine:         state.balances.mine,

        peer:         state.balances.peer,

        pendingBurns: state.pendingBurns,

        channelId:    this.channelId

      }))

    )

  }



  // Close channel — submit final state to L1

  async close() {

    const finalState = this.state

    await submitToL1({

      type:        '0x06',  // CHANNEL_CLOSE

      channelId:   this.channelId,

      finalState:  finalState,

      signature:   finalState.mySignature

    })

    // 24-hour challenge window begins

    // Mini node watchtowers monitor for fraud

  }



  // Verify peer's signed state update

  verifyPeerState(state, peerSignature) {

    const stateHash = this._hashState(state)

    const peerPair = ECPair.fromPublicKey(

      Buffer.from(this.peerPublicKey, 'hex')

    )

    return peerPair.verify(stateHash,

      Buffer.from(peerSignature, 'hex')

    )

  }

}

8.3 Fraud Proof (JavaScript Watchtower)

Mini nodes watch for fraudulent channel closes on L1. When detected, they submit a fraud proof transaction with the newer signed state.

class Watchtower {

  constructor(channelStates) {

    this.channelStates = channelStates  // Map: channelId → latest state

  }



  // Called when L1 broadcasts a channel close event

  async onChannelClose(event) {

    const { channelId, submittedState } = event

    const knownState = this.channelStates.get(channelId)



    if (!knownState) return  // Not watching this channel



    if (submittedState.nonce < knownState.nonce) {

      // Fraud detected — submit newer state

      console.log(`Fraud detected on channel ${channelId}`)

      await this.submitFraudProof(channelId, knownState)

    }

  }

    const tx = {

      type:        '0x07',  // FRAUD_PROOF

      channelId:   channelId,

      validState:  validState,

      reporter:    myWalletAddress

    }

    await broadcastToFullNode(tx)

    // Reporter earns fraud detection reward on confirmation

  }

// MusicChain network parameters

const MUSICCHAIN_NETWORK = {

  messagePrefix: '\x19MusicChain Signed Message:\n',

  bech32:        'mc',

  bip32:         { public: 0x0488B21E, private: 0x0488ADE4 },

  pubKeyHash:    0x19,

  scriptHash:    0x05,

  wif:           0x80,

}



class MusicChainWallet {



  // Generate new wallet from BIP39 mnemonic

  static generate() {

    const mnemonic = bip39.generateMnemonic(256)  // 24 words

    return MusicChainWallet.fromMnemonic(mnemonic)

  }



  static fromMnemonic(mnemonic) {

    const seed = bip39.mnemonicToSeedSync(mnemonic)

    const root = bip32.fromSeed(seed, MUSICCHAIN_NETWORK)

    return new MusicChainWallet(root, mnemonic)

  }



  constructor(root, mnemonic) {

    this.root     = root

    this.mnemonic = mnemonic

    // BIP44: m/44'/coin'/0'/0/index

    this.external = root.derivePath("m/44'/7777'/0'/0")

    this.internal = root.derivePath("m/44'/7777'/0'/1")

  }



  getAddress(index = 0) {

    const child = this.external.derive(index)

    const { address } = bitcoin.payments.p2wpkh({

      pubkey:  child.publicKey,

      network: MUSICCHAIN_NETWORK,

    })

    return address

  }



  sign(txHex, utxos) {

    const psbt = bitcoin.Psbt.fromHex(txHex,

      { network: MUSICCHAIN_NETWORK })

    // Sign each input

    utxos.forEach((utxo, i) => {

      const child = this.external.derive(utxo.addressIndex)

      const keyPair = ECPair.fromPrivateKey(

        child.privateKey, { network: MUSICCHAIN_NETWORK }

      )

      psbt.signInput(i, keyPair)

    })

    psbt.finalizeAllInputs()

    return psbt.extractTransaction().toHex()

  }



  // Secure key storage — bridges to Flutter on mobile

  async saveToSecureStorage() {

    if (window.FlutterBridge) {

      // Mobile: use hardware-backed Flutter Secure Storage

      await flutterBridge('SECURE_WRITE', {

        key:   'mc_mnemonic',

        value: this.mnemonic

      })

    } else {

      // Desktop: use WebCrypto with AES-GCM encryption

      const key = await this._deriveStorageKey()

      const encrypted = await this._encrypt(this.mnemonic, key)

      localStorage.setItem('mc_wallet', encrypted)

    }

  }



  async _deriveStorageKey() {

    // Derive storage key from user password via PBKDF2

    const password = await promptUserPassword()

    const enc = new TextEncoder()

    const keyMaterial = await crypto.subtle.importKey(

      'raw', enc.encode(password), 'PBKDF2', false, ['deriveKey']

    )

    return crypto.subtle.deriveKey(

      { name: 'PBKDF2', salt: enc.encode('musicchain'), iterations: 100000, hash: 'SHA-256' },

      keyMaterial,

      { name: 'AES-GCM', length: 256 },

      false,

      ['encrypt', 'decrypt']

    )

  }

}

11. Block Structure

11.1 Block Header (152 bytes)

Field              Size    Description

version            4B      protocol version

prev_block_hash    32B     SHA256(previous header)

merkle_root        32B     merkle root of all transactions

fingerprint_hash   32B     SHA256(constellation in body)

song_id            32B     SHA256(audio file)

timestamp          8B      unix timestamp microseconds

block_height       4B      chain height

nonce              4B      tie-breaking (XOR lottery is primary)

11.2 Block Body (variable)

Field              Size      Description

constellation      ~400KB    full Dejavu hash constellation at 25% density

transaction_count  4B

transactions       variable  UTXO transactions since last block

registration_count 4B

registrations      variable  new song registration records (~420B each)

The full constellation is embedded in every block body rather than just its hash. This anchors each block to a high-dimensional dataset unique to a specific audio recording — tampering requires reproducing a valid constellation without the original audio file, which is computationally infeasible.

12. Consensus Mechanism

12.1 Fingerprint Lottery

On block N confirmation:

  1. Submission window opens (60 seconds)

  2. Storage nodes submit valid constellations via WebSocket → mini node → full node

  3. Each submission verified:

       a. SHA256(C) not in fingerprint registry (unique song)

       b. Constellation passes statistical structure check

  4. Winner selection:

       winner = argmin XOR(SHA256(C_i), prev_block_hash)

  5. Winner's constellation written into block N+1 body

  6. Block propagated to all full nodes

  7. Winner earns bonus reward δ



XOR lottery properties:

  Deterministic:     all full nodes compute same winner independently

  Unpredictable:     prev_block_hash unknown until confirmation

  Ungameable:        each song has exactly one valid constellation

  No computation:    pure cryptographic selection, no hash race

12.2 Edge Cases

No submissions in window:

  Window extends 30 seconds (max 3 extensions = 150 seconds total)

  If still no submissions: empty heartbeat block with timestamp only



Storage node offline after submission:

  Fingerprint remains valid for consensus

  Node misses download rewards during offline period only

  No penalty — economic disincentive is sufficient

13.1 Token Flow per Download

Download count is derived trustlessly from chain:

download_count(song_id) = COUNT(Type 0x0B WHERE song_id = X)

play_count(song_id)     = COUNT(Type 0x0E WHERE song_id = X)

No local counters. Any node can independently verify any count at any time.

Condition: download_count ≤ 10,000 (discovery phase)

  Master escrow:      +0.5 × M tokens minted

  Publishing escrow:  +0.5 × M tokens minted

  Storage node:       +1 token minted        (invariant)

  Downloader wallet:  +M tokens minted

  Net:                +(M + 2) tokens



Condition: download_count > 10,000 (popular phase)

  Master escrow:      +0.5 tokens minted     (invariant)

  Publishing escrow:  +0.5 tokens minted     (invariant)

  Storage node:       +1 token minted        (invariant)

  Downloader wallet:  -B tokens burned       (from wallet balance)

  Net:                +(2 - B) tokens



Artist and storage node rewards are invariant across all supply conditions.

Only downloader mint/burn rates are dynamic.

Play events (Type 0x0E) have no token economics — analytics only.

13.2 Dynamic Rate Algorithm

Supply wave target:

  T(t) = 1.5 × 10⁹ + 5 × 10⁸ × sin(2π × t / 730)

  t = days since genesis, period = 730 days (2 years)

  T_min = 1.0B tokens (day 547, trough)

  T_max = 2.0B tokens (day 182, peak)



Supply ratio:

  R(t) = S / T(t)



Burn rate:

  B(t) = clamp(3 × R(t)², 0, 10)



Mint rate:

  M(t) = clamp(3 × (2 - R(t)²), 1, 6)



Rate update: every 1000 blocks (~2.7 hours)

Manipulation resistance: 30-day rolling average download velocity



Hard guardrails:

  S < 800M: B=0, M=6  (emergency expansion)

  S > 2.2B: B=10, M=0 (emergency contraction)

        storeCoverArt(rec.cover_hash, data.data(), data.size())

      }



      // Lyrics → hash only

      auto& lyrics = id3->frameListMap()["USLT"]

      if (!lyrics.isEmpty()) {

        auto text = lyrics.front()->toString().toCString(true)

        sha256(text, strlen(text), rec.lyrics_hash)

        // Store full lyrics to disk: /var/musicchain/lyrics/{hash}.txt

        storeLyrics(rec.lyrics_hash, text)

      }

    }

  }

  return rec

}

18. Security Analysis

18.1 Attack Vectors

Fingerprint spoofing:

  Cannot fabricate valid constellation without real audio file

  Statistical structure check on full node catches random data

  No economic reward for fake constellations



Storage node dominance (51% equivalent):

  XOR lottery is per-unique-song, not per-node

  Attacker needs unique audio files, not just compute

  Fake submissions earn nothing — economically irrational



L2 channel fraud:

  Signed state nonces prevent replay of old states

  24-hour challenge window catches fraud

  Mini node watchtowers auto-submit proofs on behalf of offline users

  Stake slashing makes fraud economically irrational



OPFS data corruption:

  SHA256(audio file) = song_id verified on every fingerprint submission

  Corrupted file produces wrong fingerprint — detected immediately

  Node loses submission reward; automatic re-download triggered



WASM integrity:

  dejavu.wasm and secp256k1.wasm hashes published on chain at genesis

  Browser verifies WASM hash before instantiation

  Tampered WASM rejected before any sensitive operations



Governance attack:

  Quadratic voting limits whale dominance

  30-day token holding minimum for full weight

  7-day voter cooling period

  Parameter change limits per proposal

  Emergency council veto

22. Decentralized Source Control and Developer Rewards

22.1 Design Philosophy

MusicChain source code lives on full node disk as a standard Git repository served by a Gitea instance. The blockchain does not store diffs or source code — it records only a lightweight commit record (commit hash + author wallet + reward tier) that triggers an automatic token payment to the developer's wallet when a commit is merged. Full nodes mirror each other's Git repositories using standard Git protocol. No GitHub dependency. No foundation. No corporate sponsor. Developer compensation is built into the protocol itself.

// mc_gitwatcher.cpp — C++ commit watcher daemon



#include <curl/curl.h>

#include <nlohmann/json.hpp>

#include "mc_rpc.hpp"

#include "mc_wallet.hpp"



using json = nlohmann::json



// Reward tiers in tokens

const std::map<std::string, uint64_t> REWARD_TIERS = {

  { "critical", 5000 },

  { "major",    1000 },

  { "minor",    100  },

}



// Classify commit by message keywords

std::string classifyCommit(const std::string& msg) {

  std::string lower = msg

  std::transform(lower.begin(), lower.end(), lower.begin(), ::tolower)

  if (lower.find("security") != std::string::npos ||

      lower.find("critical") != std::string::npos ||

      lower.find("vuln")     != std::string::npos) return "critical"

  if (lower.find("feat")    != std::string::npos ||

      lower.find("feature")  != std::string::npos ||

      lower.find("add")      != std::string::npos) return "major"

  return "minor"

}



// Handle incoming Gitea webhook POST

void onPushWebhook(const std::string& body) {

  auto payload = json::parse(body)



  // Only reward commits landing on main branch

  if (payload["ref"] != "refs/heads/main") return



  for (auto& commit : payload["commits"]) {

    std::string hash    = commit["id"]

    std::string gpgKey  = commit["author"]["email"]  // mapped via registration

    std::string message = commit["message"]

    std::string tier    = classifyCommit(message)

    uint64_t    reward  = REWARD_TIERS.at(tier)



    // Look up developer wallet from chain registry

    std::string wallet = MCChain::lookupDevWallet(gpgKey)

    if (wallet.empty()) {

      std::cerr << "No wallet registered for: " << gpgKey << std::endl

      continue

    }



    // Broadcast reward transaction

    MCTransaction tx

    tx.type           = 0x0D   // COMMIT_REWARD

    tx.commit_hash    = hexToBytes(hash)

    tx.author_wallet  = wallet

    tx.reward_tier    = tier

    tx.reward_amount  = reward

    tx.sign(nodeWallet)



    MCChain::broadcast(tx)

    std::cout << "Rewarded " << reward << " tokens to " << wallet

              << " for commit " << hash.substr(0,8) << std::endl

  }

}



int main() {

  // Start HTTP server for Gitea webhooks on localhost:9876

  startWebhookServer(9876, onPushWebhook)

  std::cout << "mc-gitwatcher started on port 9876" << std::endl

  while (true) sleep(1)

}

22.4 Developer Wallet Registration

One-time setup links a developer's GPG signing key to their MusicChain wallet. All future commits signed with that GPG key automatically earn rewards to that wallet.

Type 0x0C  DEV_REGISTRATION

  gpg_fingerprint:  20B   GPG key fingerprint (160-bit SHA1)

  gpg_pubkey:       var   Full GPG public key bytes

  wallet:           32B   Reward destination wallet address

  email:            128B  Git commit email address

  Proves developer controls both the GPG key and the wallet

3. Submits Type 0x0C transaction signed by both keys

4. Full node verifies both signatures

5. Stores GPG fingerprint → wallet mapping on chain

6. All past and future commits signed with that GPG key

Initial source tarball:
